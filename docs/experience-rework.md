# 跑团体验改造与验收

目标：第一次接触模组的 KP 导入后即可沿着主持人的思路理解故事、准备开场并获得现场参考；玩家能按本团要求完成角色；现场操作支持叙事而不要求重复登记。保留现有 P2P、稳定席位、断线补发、本地记录和受众隔离。

2026-10-12 最新反馈：用户明确这是给 KP 的参考，不需要过重的自动裁定验收。页面已简化为两个模式：“跑团辅助”默认只解析可用于跑团的基础资料；“主持参考”包含全部基础资料，再以全文梳理、逐幕规划和分批写作补充引导。基础结果可直接升级，不重新解析；参考失败也不影响使用基础资料。默认取消模型逐批审查、反复修订和总审，保留出处、结构校验及停止恢复。此前完整审查留作显式开启的开发诊断；额外重复生成已停止。设计见 [模组整理的两个模式](module-generation-pipeline.md)，此前通过率与原始失败留在 [历史内容验证记录](module-generation-validation.md)，不冒充简化路径的新评测。

## 验收问题

1. 没读原文的 KP 能否讲清楚真相、人物目的和主要调查途径？对疑点能否直接展开原文，而不用重新搜索全文？
2. KP 能否准备第一幕，并查到玩家跳过预想途径时的处理建议？建议是否清楚说明哪些是原文、哪些是补充？
3. 玩家完成角色需要查多少次规则、向 KP 提问多少次、返工几轮？
4. 一次行动中，哪些操作在重复已经发生的交流？玩家等待软件操作多久？
5. 快捷操作是否始终保留公开范围与内容边界？

### 2026-10-15：连接中断与继续跑团

再次检查 Browser 入口，仍只有 MCP Apps 后端且没有标签；未能执行双网页点击或真实 WebRTC 直连，没有绕过工具边界。沿连接代码和运行中的中继继续检查，本批完成了三项有失败复现的修复：

1. **中继掉线误伤直连认证**：传输层保留了仍可达的 DataChannel，会话层却在中继断开时无条件清空席位认证。新增 KP 端、玩家端、两端中继中断三种用例，修复前全部失败。现在以传输层报告的实际可达成员决定认证是否失效；直连仍可达时继续处理操作，两条路径都失去后暂停并重新认证。该直连场景使用可控传输模拟，并非真实浏览器 DataChannel。
2. **直连初始化异常没有完整退回中继**：浏览器缺少 WebRTC、构造连接失败、生成 offer 失败均可产生未处理的拒绝或缺失的发送成员。三种回归先失败，修复后自动保留中继成员、清理未完成的直连资源，广播可继续。退出后的迟到协商不会重新发送 offer。
3. **实际断线仍显示中继在线**：未建立 RTC 对象的玩家，在 WebSocket 断开时没有收到 offline 路径状态。真实中继测试先得到 `relay` 而非 `offline`。现补上无 RTC 对象时的离线通知，避免界面仍允许依赖在线状态的操作。

本批新验证：运行默认传输配置（`COC_ROOM_LIVE_DEFAULT_TRANSPORT=1`），不使用强制中继开关。Node 环境没有 WebRTC API，因此实际传输自动退回本机 WebSocket 中继，日志确认出现 relay、没有 direct。主动关闭玩家的真实 WebSocket而保持 RoomSession 存活，确认自动重连、补齐离线期间的公开场景变化、继续提交行动；随后停止并重建 KP 会话，确认从同一仓库恢复场景、玩家重新认证并继续行动。离线期间写入的 KP 私密事件在玩家记录中仅有 redacted 占位，不含秘密正文。

连接、席位认证和实际中继共 38 项通过；旧版会话和应用外壳回归 18 项通过，合计 56 项。类型检查、网页构建、差异格式检查通过。证据保留在 `.tmp/direct-survival-before.log`、`.tmp/rtc-fallback-before.log`、`.tmp/relay-offline-before.log`、`.tmp/connection-recovery-verified.log`、`.tmp/connection-recovery-regression.log` 和 `.tmp/connection-recovery-build.log`。
