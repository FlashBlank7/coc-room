# 主持工作流内容验证记录

日期：2026-10-12。目标是检查未读原文的 KP 能否依据生成参考主持，而不是检查输出是否长得像试阅包。

后续范围调整：用户要求简化为“跑团辅助”和包含前者全部资料的“主持参考”。额外重复生成已停止并保留结果；页面默认不再运行下述完整语义审查。本文保留此前诊断证据，不把其通过率移用为新简化路径的评测结果。当前两模式的交互与数据保留由针对性自动测试验证，未继续开展冗长的模型验收。

## 方法

原文实际提取 → 实际 Codex 工作流生成 → 独立读者回答主持问题 → 独立验收对照原文。读者只得到生成正文和问题，不得到原文、出处引文、事实台账或标准答案。验收者同时核对答案是否得到候选正文支持，不能用原文替候选补答案。程序另行检查读者引用确实存在。

这是自动阅读模拟，不是真人盲测。模型使用本机 Codex CLI 配置的默认值，没有声称固定某个模型版本。所有生成正文均由模型产出，没有手改为标准答案。调试中修改的是通用提取、提示、审查及修订代码。

主样本是用户提供的《见世之蝶》完整原文，13,352 字符；重新提取为 14 个场景。两个跨结构样本是原创受控短模组：末班车的线性倒计时调查、潮汐账簿的自由地点调查与状态变化。它们用于暴露不同错误，不代表两份已经过真人实跑的商业模组。

## 实测发现并修复的问题

- 提取后线索与场景的关联不对称；不同场景的同名技能可能关联到错误结果。现在双向归并，并优先采用本场完整检定。
- 分批审查把后续才发生的条件当作当前幕缺失，导致重复修订。批次审查只检查当前适用内容，整包审查负责全局覆盖。
- 中间台账误读原文后，写作与审查会共同维护这个错误。审查现在可以用逐字原文依据纠正台账，再独立复核正文。
- 全局审查指出问题，却没有触发对应总览或场景修订。现在保存受影响批次的修订队列，合并后再审查整包。
- 整批修订超长、慢，并可能漏改小问题。现在只生成受限字段补丁，程序原子合并，不重写其余正文；非法路径、引用或删除必要内容会被拒绝。
- 建议里只有“照常调查”“KP 另行安排”，实际仍要求回原文。现在要求给出下一处地点、第一位可询问的人或可检查的物件；原文空白须另列具体建议，保留原作限制。
- 网页等待长调用时超过五分钟没有响应头，出现 `Failed to fetch`。本地桥已为主持生成启用固定心跳；一次真实修订约 600 秒仍正常返回。

## 结构相同但内容错误的测试

保留合法结构，分别注入：开场混入失踪后的现场状态、提前公开真名、把只被提及的 NPC 放在现场、逆序调查仍无条件给祝福/幻境、无需检定就给出知识成功结果。真实产品审查抓到了这五个注入问题。它证明审查对这些语义错误有反应，不代表没有误报，也不代表每种错误都能自动修好。

## 失败记录与验收口径

失败的模型输出和验收没有被最终通过结果覆盖。`butterfly-r1` 是因网络超时诊断而停止的运行，不算完成样本；恢复运行可能混用调试前后的通用提示，不能当作最终版本一次从头生成的证明。

验收题目有过校准，旧报告均保留。例如，“谁为何请调查员查案”没有明确询问召唤失败后的退路，但评分要求这个细节；完整候选已有退路，读者漏答，原报告为 9/10。新版问题明确追问失败退路，标准答案不变。另一题由“人物是否绝对不在场”改成实际操作问题：能否仅因为侍女提及他们就安排他们在场。它允许如实说明原文未安排其现身，并仍禁止添加在场 NPC。不能把新题结果冒称为旧题原始通过率。

## 工程验证

最终前端全量 610 项通过、15 项按环境跳过；Python 231 项、协议 98 项通过。类型检查、网页构建、Windows 原生构建及冻结解析器 UTF-8 冒烟通过。原生构建中发现新增测试夹具的字面量类型过宽，修正后重建通过。测试与构建不能替代上面的正文验收；未进行本轮浏览器点击或真人多人试玩。

## 范围限制

目前有一份用户真实模组和两份受控短模组的实际生成证据，不足以承诺任意模组稳定达到同一质量。没有真人备团耗时或现场节奏测量；真实 DeepSeek 生成未测试。长篇超过单步容量时明确保留进度并报错，尚未实现任意长度的分章约束归并。结构提取漏掉整处实体时，也没有自动回到提取节点补建的通路。短模组整轮仍需约 13—14 分钟，等待时间是实测存在的产品问题。
