# CoC Room 人类使用模型

本文不是功能清单，而是界面和交互的验收基准。任何新增功能都必须先回答：它在真实跑团的哪个时刻被谁使用？它是否打断了叙事？如果只能通过阅读说明书理解，就不应出现在默认路径里。

## 1. 我们服务的不是“VTT 管理员”

CoC 的核心是共同创造一段调查与恐怖故事。Chaosium 将其描述为由 KP 提供故事结构、调查员共同探索，规则与骰子只在结果不确定时裁定。玩家不应先学习一套数据库或画板编辑器才能开始游戏。

参考：

- [Chaosium CoC 7 版快速入门](https://www.chaosium.com/cthulhu-quickstart/)
- [Chaosium Starter Set 对角色分工的说明](https://www.chaosium.com/call-of-cthulhu-starter-set-pdf/)
- [Chaosium Keeper Screen 的定位](https://www.chaosium.com/call-of-cthulhu-keeper-screen-pack-pdf/)

产品定位因此是：

> 一个把 KP 已准备的模组，在开团时变成“下一步该做什么”的调查工作台；而不是把所有底层对象同时展示出来的通用 VTT。

## 2. 真实任务分成两个世界

### 开团前：准备模式

KP 的实际任务顺序：

1. 选择并通读模组，理解真相、时间线和结局。
2. 摘出本次可能使用的场景、地点、NPC、核心线索和检定后果。
3. 准备玩家可见的描述、手记、图片和可选地图。
4. 选择本团模组并创建房间；建房和“把模组带入房间”是两个必须被明确确认的动作。
5. 建房后第一份专属邀请直接出现在现场主路径，复制前不能因席位创建而消失；后续邀请和换新凭据再进入低频席位管理。
6. 玩家加入，创建或带入调查员；填好基本字段即可带入房间，属性生成方式由各团在桌面上自行约定。
7. 开团前只检查“人到齐、角色就绪、开场场景就绪”，不要求补齐所有高级资源。

社区经验反复提到：KP 会把地点、NPC、线索、事件顺序和原文页码整理成短要点，而不是在游戏中重新阅读整本模组；过度准备图片、地图和自动化会显著增加负担。

参考：

- [Chaosium：跑长团前先完成 groundwork 和 Session Zero](https://www.chaosium.com/blogrunning-the-children-of-fear-campaign-part-four-keeper-advice-from-the-writer-herself-lynne-hardy/)
- [实际 KP 的准备方法：地点、NPC、线索与简短要点](https://www.reddit.com/r/callofcthulhu/comments/hss14o)
- [实际 KP 的准备重点：时间线与关键线索位置](https://www.reddit.com/r/callofcthulhu/comments/yqwtuq)

### 开团中：游玩模式

KP 的高频循环：

1. **呈现当下**：玩家现在在哪里、看见谁、已经知道什么。
2. **等待意图**：玩家用自然语言描述想做什么。
3. **作出裁定**：直接给信息，或在存在有意义的不确定与代价时要求检定。
4. **结算后果**：成功、失败或带代价推进，而不是让调查停住。
5. **公开新信息**：展示地点描述、NPC、手记或线索。
6. **推进焦点**：进入下一情境，再回到第 1 步。

检定不是一个随时可点的骰子工具，而是一段由叙事触发的协商。Chaosium 的 7 版快速规则明确要求玩家先描述目标和做法，由 KP 判断结果是否同时具有不确定性与戏剧性；只有满足时才要求检定并给出难度。第一次检定失败后，玩家可以提出一种新的做法申请“强推”，但 KP 必须先说明再次失败可能带来的严重后果，再让玩家决定是否承担风险。因此现场产品模型应是：

1. 玩家描述“想达到什么、准备怎么做”，技能数值只是建议。
2. KP 选择直接给出信息、说明当前不可行，或确定一次检定。
3. 掷骰完成后先回到叙事后果，不把失败变成无上下文的红色数字。
4. 可强推的失败只出现一次“换一种做法并申请强推”；普通失败不能直接重复点击骰子。
5. KP 批准强推时必须先写清失败代价，玩家读到代价后才拥有第二次掷骰按钮。
6. 强推结果不能触发无限再次强推；无论成功还是失败都回到 KP 叙述与公开新信息。

参考：

- [Chaosium CoC 7 版快速规则：只有结果不确定且具有戏剧性时才检定](https://www.chaosium.com/content/FreePDFs/CoC/CHA23131%20Call%20of%20Cthulhu%207th%20Edition%20Quick-Start%20Rules.pdf)
- [Chaosium 规则 Wiki：先约定目标，再由 KP 判断是否检定及难度](https://callofcthulhuwiki.chaosium.com/rules/game-system.html)

NPC 一旦在当前情境登场，交谈入口就应出现在该 NPC 身上；不要求 KP 或玩家去房间工具里重新查找同一个人物。KP 创建面板前必须明确选择房间公开或定向席位，且不能选择本来无权看见该 NPC 的席位。面板内的人类消息显示角色名与稳定席位名，不使用无法区分参与者的统一“调查员”标签。自动扮演只是交谈面板的可选辅助，停止入口必须始终可见。

玩家的高频循环：

1. 看懂当前情境与当前可做的事。
2. 说出行动或问题。
3. 收到 KP 请求时掷骰。
4. 查看新公开的线索，并可把重要线索标记到自己的调查栏。
5. 偶尔打开角色卡；地图存在时移动自己的棋子。

新公开的线索、手记和笔记提示必须持续到玩家真正打开共同案卷，不能因为 KP 随后说了一句话而消失；现场记录中的公开资料应当直接显示其可见附件，而不是只留下一个标题。“加入我的线索栏”是非独占的个人重点标记：不会拿走共同线索，多位调查员可以同时关注同一项，玩家也能从“我的重点”中随时移除自己的标记。加入和移除都是独立事件，不得用编辑、锁定或归档共享线索来冒充。案卷默认只渲染一份正文，通过“全部线索 / 我的重点”切换整理；可选推理板在案卷内直接打开，即使现场仍在使用另一张地图。

模组中“线索位于某地点 / 由某 NPC 提供”的关系只能作为 KP 的准备提示，不能成为游玩时的发布权限。真实调查经常需要把关键线索移动到更合理的场合，或者在玩家卡住时通过另一名 NPC、档案或现场细节补出。因此导演台应优先展示“与当前情境相关”，同时始终允许按名称搜索全部尚未公开线索；发布动作记录当时的叙事来源，但不改写房主资料库中的原始关系。

这两个循环必须在一个视野内完成。邀请管理、AI 模型、修订号、事件序号、资源哈希和协议状态属于低频诊断信息，默认折叠。

## 3. 场景、地点与地图的真实关系

- **当前情境**是叙事焦点，必须存在，即使没有图片或地图。
- **地点**是可以被公开的世界信息，可在多个情境中复用。
- **地图/画板**是可选的视觉辅助；没有地图也必须能完整跑团。
- **棋子**是人物在某张画板上的一次表现，不是角色卡本身；同一人物可以没有棋子，也可以在不同画板拥有不同摆放。
- **棋子移动**可以提示 KP 玩家进入某区域，但不能自动泄露描述、NPC 或线索。
- 玩家默认只能操作自己控制的调查员棋子；KP 可以操作全部棋子并决定移动是否改变当前情境。
- KP 可以在自己预览场景后，用一次明确动作“向玩家呈现”，而不是依赖拖拽这一种隐蔽手势。

Foundry 的实践同样区分“GM 自己查看场景”和“激活场景让全部玩家进入”，并允许将 Journal/Handout 定向展示给玩家；Owlbear Rodeo 则把核心限制在地图、棋子、绘制和迷雾，以换取更低学习成本。

参考：

- [Foundry Scenes：查看与激活是不同动作](https://foundryvtt.com/article/scenes/)
- [Foundry Tokens：棋子是场景内的独立表现，并按控制权允许用户操作](https://foundryvtt.com/article/tokens/)
- [Foundry Journal：内容可展示给全部或指定玩家](https://foundryvtt.com/article/journal/)
- [Owlbear Rodeo：前五分钟只要求 GM 建场景、玩家点邀请加入](https://docs.owlbear.rodeo/docs/getting-started/)

## 4. 信息架构

### 未进入房间

- **开始**：继续上次调查、作为 KP 开团、作为玩家加入。
- **我的调查员**：个人角色库；不混入房间运维。
- **KP 备团**：模组解析、阅读、修订和资源准备。
- **设置**：网络与 AI 等低频配置。

### 已进入房间

默认只显示三个任务区：

- **现场**：当前情境、可选地图、对话和当前待办。
- **线索**：全员已知内容、我的重点线索、可选关系板。
- **记录**：人类可读的对话、检定和重要公开事件。

KP 额外拥有一个按需展开的 **导演台**：

- 推进情境。
- 公开地点、NPC、线索或手记。
- 从模组再次公开同一地点、NPC、线索或手记时更新原房间条目，不制造重复项，也不清掉跑团中追加的场景关系、人物数值、附件或玩家整理结果。
- 源 ZIP 中通过解析器校验的静态图片只按 SHA-256 重新匹配；文件名和归档路径不成为素材身份。KP 必须先在本机看到预览，再明确把图片收入模组素材。
- “收入模组素材”不等于绑定背景，更不等于发布。房间里从模组素材选择图片后仍要经过一次仅 KP 可见的预览和“确认公开背景”。
- 响应待处理的检定。
- 查看场景私密要点。

房间邀请、席位轮换、图片生成、NPC 属性生成和自动 NPC 属于 **房间工具**，不与高频导演动作混排。

## 5. 默认界面的硬性规则

1. 一个区域只允许一个视觉主动作；其余操作使用次级按钮或菜单。
2. 默认文案使用人的语言：不用 `V2`、`r3`、`连续游标`、`entity`、`artifact`、`audience`。
3. 空状态必须告诉用户“为什么为空”和“下一步点哪里”，不能只写“暂无”。
4. KP 与玩家看到不同的工具，不靠禁用一大片按钮区分权限。
5. 玩家不显示红acted 占位事件；秘密序号只用于内部同步。
6. 低层画板移动、资源同步和修订事件不污染人类聊天记录。
7. 没有模组、地图、图片、AI 或音频时仍可创建角色、邀请玩家并完整跑团。
8. 场景切换、公开内容和要求检定都要有明确的受众反馈。
9. 危险动作描述后果，例如“归档后本次房间不再显示”，而不是只显示动词。
10. 首次使用依靠就地引导完成，不把文档当作主流程的一部分。
11. AI 解析草稿、人工修正和待处理原文不得因切换主导航而静默丢失。
12. KP 浏览历史场景时不能继续用“当前情境”的名义公开地点或 NPC；必须先明确切换场景。
13. 图片生成和同步音频在开始前显示用途、目标和当前状态，且禁止重复提交。
14. 任何自动 NPC 回应都必须在折叠面板之外保留“立即停止”和运行/失败状态。
15. “角色基本资料已填”不能被描述为“通过 CoC 规则校验”；应用只检查基本字段，规则核对交给桌面上的人，不设强制确认步骤。
16. “已经邀请”和“当前在线”必须分开显示；玩家离线后稳定席位仍留在 KP 名单中，换新邀请前必须说明旧邀请失效且会让在线玩家暂时断开。
17. 新公开线索、手记和笔记的未读状态只在玩家实际打开案卷后清除；案卷入口不得承诺一个点击会自动完成尚未发生的“加入我的线索栏”。
18. 已收起的模组线索必须能以同一条线索的新修订恢复，不能显示一个点击后无事件的伪按钮。
19. 模组抽取出的地点、NPC 与线索关系只用于推荐和定位，不能锁死线索的实际发布位置；关键调查信息不能因预设关系不匹配而无法推进。
20. 棋子拖拽结束后要保留玩家看到的新位置，直到房主确认或明确拒绝；网络往返期间不能先弹回旧位置，让玩家误以为操作失败。
21. 解析完成或人工修正后的模组草稿必须留下本机恢复点；恢复点不能出现在正式模组库、不能自动用于房间，也不能把源文件字节或服务凭据写入其中。
22. 网页记录只读取本席位可见事件引用的本机媒体；能安全嵌入的图片/音频必须离线可读，缺失或过大的媒体必须在原事件位置解释原因，不能用“自包含”掩盖附件丢失。
22. “不需要检定，直接叙述结果”必须是一等裁定路径；不能迫使 KP 创建一个必定成功的伪检定才能继续故事。
23. 角色、NPC 与棋子摆放必须解耦；删除或移动一张画板上的棋子不能删除人物资料，也不能暗中改变其他画板上的表现。
24. 玩家提交的是“目标 + 做法”，技能仅为可选建议；实际采用的技能、目标值、难度和奖惩骰必须由 KP 在裁定时明确决定。
25. 检定后的叙述必须绑定到触发它的那次行动；多人并行时，给另一位玩家的聊天、线索或场景切换不能让当前玩家误以为自己的结果已经结算。
26. “让 NPC 登场”和“把 NPC 棋子放到画面”必须是两个动作；前者公开玩家可见摘要，后者只增加一个可移动的视觉表现，同一 NPC 可有零个或多个表现棋子。
27. 没有本地安全桥的网页页签必须明确显示能力边界，不能把“无法检查宿主凭据”伪装成 Codex 未安装或 DeepSeek Key 缺失；真实 AI 操作停用时，联机、导入成品和模拟 UI 仍可使用。

## 6. 可用性验收任务

新手不阅读说明，应能完成：

### KP

1. 在 60 秒内找到“导入模组”。
2. 在 90 秒内创建房间并复制第一位玩家邀请。
3. 进入房间后，无地图也能呈现第一个场景。
4. 在玩家提出行动后，10 秒内找到“要求/允许检定”。
5. 在 10 秒内公开一个地点、NPC 或线索，并清楚知道玩家将看到什么。
6. 从已保存模组创建新团时，始终知道房间是否已经创建、模组是否已经真正带入。
7. NPC 登场后，可直接从人物卡开启/打开交谈；自动回应运行时无需展开工具即可停止。

### 玩家

1. 粘贴邀请后不理解“席位、令牌、协议”也能加入。
2. 没有角色时能看到唯一明确的下一步。
3. 入团后第一眼知道“现在在哪里、发生了什么、轮到我做什么”。
4. 只在 KP 允许后看到一次明确的掷骰按钮。
5. 一次失败后能说明新的做法申请强推；必须先看见 KP 给出的失败代价，才能决定是否进行唯一一次重掷。
6. 新线索出现后能打开并标记，不需要理解画板对象模型。
7. 能在当前登场人物卡上进入独立交谈，不必去工具列表再次寻找 NPC。
8. 长团记录能按对话、检定、发现或角色状态检索，且筛选不会意外裁掉导出内容。

## 7. 不用功能数量衡量进度

一次迭代只有在减少以下任一指标时才算可用性进展：

- 完成核心任务需要访问的页面数。
- 同一时刻可见的主按钮数。
- 必须理解的系统术语数。
- KP 在玩家等待时需要执行的点击数。
- 玩家需要向 KP 询问“我该点哪里”的次数。

如果新功能增加这些负担，必须采用渐进披露、默认值或自动推导抵消成本。
